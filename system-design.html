Authorization model — Keto OPL

Namespace graph dari keto-schema.opl: application → module → division → role → permission. Panah dibaca sebagai relasi ("Module app Application"). Contoh konkret di bawah memakai data shop/billing.

Example tuples — shop/billing

Application:shop
Module:shop:billing      #app → Application:shop
Division:shop:billing:emea  #module → Module:shop:billing

Role:shop:billing:emea:accountant
  #division → Division:shop:billing:emea
  #member → User:alice, User:bob
  #member → SubjectSet(Role:…:finance-lead, "member")  ← seniors inherit down
Role:shop:billing:emea:finance-lead
  #member → User:carol

Permission:billing.invoice.read
  #granted → Role:…:accountant
Permission:billing.invoice.refund
  #granted → Role:…:finance-lead

Enforcement — active role, no escalation

  • Picker: GET /relation-tuples?namespace=Role&subject_id=alice → list her roles.
  • ① Validate: Role:accountant#assume @ alice → may she act as it? (follows member SubjectSet nesting)
  • ② Authorize: Permission:invoice.read#granted @ Role:accountant → does this role hold it?
  • Never Permission#check @ alice alone — that passes via any of her roles.
  • Delegated admin: Role:…#manage traverses up to the division admin.

Design decisions

Edge — Traefik v3.7

  • Single entrypoint :80/:443; ACME via Let's Encrypt.
  • Host() routing (Docker labels, no static config): auth.example.com → sso-auth :3000 · iam.example.com → sso-iam :3000 · api.example.com → Oathkeeper :4455. Same image, APP_MODE differs.
  • Rate-limit + headers middleware at the edge. Chosen over Nginx for native service discovery.

Zero-trust network

  • Only Traefik publishes host ports. Everything else is on internal:true Docker networks.
  • Admin APIs (Hydra :4445, Kratos :4434) never leave the intranet.
  • External apps touch public OAuth2 endpoints only.

Scaling

  • Kratos, Hydra, Oathkeeper, Keto, Next.js are stateless → scale horizontally.
  • Postgres is the stateful tier — add read replicas + PgBouncer when needed.
  • Oathkeeper caches Hydra JWKS/introspection to survive spikes.

Security notes

  • Secrets via env / Vault, never baked into images.
  • Keto authorizes every request; short-lived access tokens + refresh rotation.
  • Optional Cloudflare in front for WAF / DDoS (Traefik has no full WAF).

auth vs iam — “pintu vs akun”

  • auth.example.com — unauthenticated flows: login, register, recovery, logout, OAuth2 consent.
  • iam.example.com — everything needing a session: settings, MFA, sessions, admin console.
  • Rule: kalau butuh login dulu → iam. One codebase, route-separated; split deployments only when teams or security policies diverge.

Shared session cookie

  • Kratos cookie domain .example.com — one SSO session readable on both subdomains.
  • One identity, one login. “Admin” is not a user type — it’s a Keto relation (Division#admin); menus hide/show based on a Keto check.

Data ownership

  • One Postgres, one database per service (kratos_db, hydra_db, keto_db…) — isolated migrations, small blast radius.
  • Keto is the source of truth for authz; Kratos for identities. No parallel roles table in app_db — nothing to sync, nothing to drift.
  • Next.js apps never touch Postgres directly — identity/permission access always goes through Ory APIs.

SMTP relay (courier)

  • Kratos courier renders email templates (verification, recovery) and hands off to SMTP.
  • Use a transactional provider (SES / Postmark / Mailgun) — SPF/DKIM/DMARC, retries and sender reputation handled for you.

External apps — standards, not SDKs

  • External apps integrate via standard OIDC using their own ecosystem libraries (Auth.js / Better Auth, Socialite, AppAuth…).
  • No proprietary client SDK to maintain. We publish an integration contract: discovery URL, scopes, the roles ID-token claim, and the X-Active-Role header convention.
  • Optional GET iam.example.com/api/my-roles (Bearer access token) lets apps refresh the role list without re-login; enforcement stays at Oathkeeper + Keto.
